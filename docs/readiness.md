# Готовность staging и production

## Значения, которые предоставляет владелец среды

Для каждого контура нужны BotFather bot token/username/Direct Mini App short name, отдельный webhook secret и HTTPS-origin; Supabase URL, publishable/service-role keys, ES256 signing pair и `kid`; числовой owner Telegram id; session/internal secrets; выделенные DB backup-reader и Storage Auth backup-reader; project CA; независимый зашифрованный S3 target; отдельные freshness/restore archive readers; пустой restore-drill project. Значения вносятся непосредственно в защищённые Environment/Vault. `.env.example` — перечень полей, а не место хранения.

Staging и production никогда не используют совместно одного бота, Supabase project ref, session secret, Vault, backup prefix или drill target. Target обязан принадлежать другому провайдеру/account, не Supabase source. Production-доступы выдаются минимальному числу операторов с MFA и записанным владельцем ротации.

## Безопасный порядок проверки

1. Установить точные Node/pnpm и выполнить frozen install, lint, typecheck, полный Vitest/PGlite, Bats, ShellCheck, production build, весь локальный Playwright matrix без внешних доступов (desktop light/dark, Telegram Web, Android portrait/landscape, iOS WebKit), отдельный `next start` smoke заголовков и браузерного gate, production audit и gitleaks.
2. Предоставить отдельные staging-ресурсы: Supabase project и пустой restore-drill project, стабильный Vercel origin, Telegram bot, независимый S3 endpoint/bucket/prefix. Получить staging-only keys и secrets, создать два значения Vault, не включая Cron или webhook. Этот этап может требовать платного capacity, но ещё не меняет app data.
3. Зафиксировать публичные identities в `config/staging-identities.json`, ограничить GitHub Environment `staging` веткой `main`, заполнить точные variables/secrets и актуальный Vault snapshot. Создать `staging-drill`: только `main`, независимый reviewer, запрет self-review, archive read/list credentials и изменяющие credentials только пустого drill target; app, Telegram, production и backup-writer secrets туда не помещать. Создать отдельный `staging-promotion` без provider secrets, также main-only, с независимым reviewer и запретом self-review. Затем выполнить ручной `migration_mode=none`, `evidence_mode=draft`; все preflight-проверки должны пройти без изменения provider data.
4. Выполнить `migration_mode=apply`, затем отдельный `migration_mode=reapply` с project-bound acknowledgement. Подтвердить checksum ledger, browser grants/RLS и приватный Realtime с выключенными публичными каналами.
5. Развернуть тот же commit на закреплённый staging origin и проверить HTTPS, CSP/security headers, Telegram browser gate, приватные download headers и отсутствие секретов в browser bundle, artifacts и logs.
6. В BotFather создать Direct Mini App, Main Mini App/Menu Button; владелец открывает личный чат и выполняет `/start`. Через Bot API private curl config установить webhook с secret token и `allowed_updates`, проверить `getWebhookInfo`, forged/stale initData, одноразовый invite, task isolation, cross-site iframe-cookie в Telegram Web и authenticated group/channel no-op/dedupe.
7. Применить scheduling SQL к уже созданным Vault secrets, выполнить reminders и cleanup вручную, затем проверить suppression, dead-letter, lease recovery, Storage 404 и orphan grace.
8. Создать Auth backup-reader без app membership, подставить его UUID в configure/inspect Storage SQL. В staging доказать: list/get `workspace-files` разрешены, put/delete и другой bucket запрещены. Generated Supabase S3 keys не использовать. Создать DB `smoking_zen_backup_reader`, интерактивно установить пароль, выполнить inspect: read-only/BYPASSRLS, полное SELECT-покрытие, zero write/membership/SECURITY DEFINER. Проверить session-mode Supavisor 5432 или оплаченный direct IPv4, `verify-full` и CA.
9. `show server_version_num` определить фактический major и выбрать закреплённый `BACKUP_POSTGRES_MAJOR`. В ручном `Staging data operations` последовательно выполнить `backup-dry-run`, один `backup-snapshot`, `freshness` и `restore-drill`; для restore передать snapshot id и точное `RESTORE_ISOLATED_TARGET:<drill-project-ref>:<snapshot-id>`. Сверить sourceProjectRef, server/client major, row counts, ready attachments, managed Supabase bootstrap, data-plane RPO/RTO и отсутствие путей/секретов в выводе. Для backup/freshness сохранить run ID/attempt и exact-byte SHA-256 из 90-дневных artifacts `staging-backup-manifest-<run_id>-<run_attempt>` и `staging-freshness-manifest-<run_id>-<run_attempt>`; для restore — run ID/attempt и exact-byte SHA-256 скачанного `staging-restore-evidence.json` из artifact `staging-restore-evidence-<run_id>-<run_attempt>`. Отдельным таймером провести полный service-recovery до Telegram/app smoke; локальный drill не подтверждает project RTO.
10. Заполнить redacted candidate по `staging-evidence.example.json` и выполнить `migration_mode=none`, `evidence_mode=complete` на том же commit. `STAGING_EVIDENCE_CANDIDATE_VALID`, в том числе полученный локально, подтверждает только форму, commit, migration manifest и публичный паспорт, но не provider state. Job `verify` публикует candidate artifact; независимый reviewer пересчитывает hashes по credentialed sources из шага 9 и только затем одобряет ожидающий job `promote` в `staging-promotion`. Только `STAGING_PROMOTION_APPROVED`, утверждённый 90-дневный candidate/receipt, исходные provider artifacts и GitHub Environment audit trail допускают go/no-go review.
11. Повторить конфигурацию отдельными production-значениями, провести smoke без пользовательских данных, включить Cron и GitHub schedules, назначить оповещения и владельца инцидента.

Credentialed проверка провайдеров backup/restore, Telegram, Supabase Cron/Vault и Vercel выполняется в staging как следующий этап запуска. Локальные fake-provider, schema-тесты, вручную заполненный `state: complete` и `STAGING_EVIDENCE_CANDIDATE_VALID` не объявляются доказательством доступа к облачным аккаунтам. Production не включается до успешного staging snapshot и restore drill, проверяемых исходных artifacts, независимого approval и promotion receipt.

## Критерии запуска

Production build без секретов успешно завершается; защищённые серверные операции при неполной runtime-конфигурации fail-closed отвечают до эффектов. GitHub production Environment допускает только `main`, требует reviewer, а production jobs имеют такой же job-level guard. В репозитории нет секретов; миграции fresh/upgrade/reapply зелёные; webhook и внутренние маршруты аутентифицируются до чтения тела; напоминания немедленно перепроверяются; cleanup не удаляет родителя до подтверждения Storage; backup manifest публикуется последним и freshness укладывается в 26 часов; drill доказывает data-plane RPO не более 24 часов и data-plane RTO не более 4 часов. Для каждого расписания настроено наблюдение за задержкой GitHub/Cron, а для rotation/dead-letter существует назначенный оператор.

Document-пайплайн в staging отдельно проверяется на том же Node 24 runtime: пассивные PDF/DOCX/XLSX проходят, а active PDF, external/DDE/XLM/network OOXML, превышение 500 PDF-страниц и структурных лимитов завершаются до публикации ready-файла.

## Остановка запуска

Запуск прекращается при любом high advisory, ошибке secret scan, публичном bucket/channel, совпадении source и backup endpoint, неполном manifest, несходящихся row/file hashes, неоднозначной роли владельца, необъяснённом `delivery_indeterminate` или отсутствии свежего восстановления. Возобновление допускается после устранения причины, повторного полного набора проверок и одного ограниченного staging smoke.
